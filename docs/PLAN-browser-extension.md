## 1. 这是一条线路：两个产品，靠文件交接

用户的问题发生在浏览器里：读到好文章时想留下 Markdown，但文章可能是登录后才看得到的、图片可能挂在带会话的 CDN 上。这件事**只有浏览器插件能做**，因为只有它手里有当前这份会话。

但插件只管「抓下来」，不管「加工」：图片还在网上，内容可能不是中文。批量加工（图片落到本地、翻译）属于桌面端已有的能力范围。

| | 插件（B） | 桌面端（A） |
| --- | --- | --- |
| 职责 | 用当前会话抓当前页 → 转 Markdown → 连图一起落盘 | 吃一批本地 `.md` → 内嵌图片 / 翻译 → 输出到目标目录 |
| 位置 | 浏览器里 | 本机应用 |
| 输入 | 当前页面 | 一个目录 |
| 输出 | 一个目录 | 另一个目录 |

**连接方式是文件交付，不是主从调用**：插件不需要桌面端在运行，也不需要任何常驻服务。若要插件必须等桌面端在场才能用，「一键导出」就失去意义了。

```
网页 → 插件：提取正文 → 转 Markdown → 写盘（标题.md + 标题.images/）
                                              ↓
                        桌面端：选目录 → 勾选 → 内嵌图片 / 翻译 → 输出到目标目录
```

## 2. 分工与顺序

| 块 | feature | 内容 | 顺序 |
| --- | --- | --- | --- |
| A | `feat-042` | 桌面端「文档处理」：选目录 → 列 md → 勾选 → 内嵌图片 / 翻译 → 输出 → 去重 | **先** |
| B | `feat-040` | 浏览器插件：提取正文 → 转 md → 收图 → 落盘 | 后 |

**为什么 A 先**：

1. B 的产物要有人接。没有 A，插件导出的 md 还得手动加工。
2. A 可以用**任意现成的 `.md` 独立验收**，不依赖插件存在。
3. 项目硬约束「同一时间只允许一个 `in-progress`」（`init.sh` 断言），两块只能串行。

## 3. 交接契约（只在本文件写一次）

插件与桌面端之间的**唯一接口是文件系统**。以下约定两边都不许各自改动：

| 项 | 约定 | 依据 |
| --- | --- | --- |
| 插件落盘位置 | 系统**下载目录根**（相对路径） | MV3 硬限制：写绝对路径报 `Invalid filename`（探针实测）；用户已选「下载根目录」 |
| 文件形状 | `标题.md` + 同级 `标题.images/` 目录 | 与 Obsidian / Typora 一致，便于后续工具处理 |
| 图片引用 | 正文用**相对路径**引用 `标题.images/xxx` | 目录可整体搬移，md 不绑死绝对路径 |
| 抓不到的图片 | **保留原始 URL，并在文中明确标记** | 签名会过期的图床（社媒类）必然失败，必须可见，不能静默丢 |
| 桌面端输入 | 用户自选任意目录（默认指向下载目录） | A 是通用能力，不绑死插件 |
| 去重依据 | 文件路径 + 内容哈希 + mtime（+ 输出路径） | 只用路径会在改名 / 移动后失效；只用 mtime 判断不了内容是否变化 |

**待定（写 FSD 前要定）**：标题里的非法字符（`/` `:` 等）怎么净化；同名文章（标题相同）是覆盖还是加后缀。

## 4. 共同口径与边界

1. **只读当前页面 DOM**：不读 Cookie、不读登录凭据、不绕过访问限制、不做自动翻页或爬取。
2. **内容不离开本机**：插件不主动联网（除浏览器自己为图片发起的下载）；翻译全部在桌面端，使用用户自己配置的端点。
3. **不静默丢东西**：抓不到的图片留 URL + 标记；处理失败要说原因。
4. **两端输出必须一致**：同一篇文章在插件导出与桌面端转换，Markdown 结果应当相同 —— 这是共享代码的理由（§5）。

---

## 5. 线路级工程决策

1. **同仓库**：插件与桌面端在同一个仓库。理由不是共享整条管线（插件大部分用不上），而是共享**「提取正文 + 转 Markdown」这一小段**，否则两端输出会漂移。
2. **共享代码边界**：抽出**无 Node 依赖**的一段（Readability + Turndown + GFM + DOMPurify），两端共用。桌面端现有的 `extract.ts` / `markdown.ts` 只是用 jsdom **合成** DOM；在插件里 DOM 本来就在手上，替换是机械的，不是重写。
3. **独立版本线**：插件的版本由扩展自身 manifest 的 `version` 管理，**不进** `desktop:release` 门禁。作废文档里的 `v0.5.0 / v0.6.0 / v0.7.0` 不采纳。
4. **触发方式**：用户主动，独立功能入口 —— 插件侧是浏览器工具栏；桌面端侧是独立页面 / 区块，不是常驻主流功能。
5. **翻译只在桌面端**：插件不碰任何密钥，因此不存在密钥存储问题。

## 7. 未验证与风险

| 项 | 为什么未验证 | 影响 |
| --- | --- | --- |
| 真实 Chrome 中是否静默写盘 | 探针里下载被测试框架接管，且无 UI | 取决于用户浏览器的「下载前询问保存位置」设置，**非代码可控** |
| N 张图 = N 个下载条目 | 无头模式无 UI | 体验问题；Chrome 会把同来源下载归组显示 |
| MV3 后台休眠打断批量下载 | 未压测 | 实现时需专门保活 |
| 超大真实页面性能 | 只测了小页面 | DOM 克隆 + Readability 在大页面上会变慢 |
| 特权页面（`chrome://` 等） | 浏览器限制 | 无法注入，属预期行为 |
| 标题非法字符 / 同名文件 | 未测 | 见 §3 待定 |

## 8. 非目标（线路级）

- 不做 Firefox / Safari 版本。
- 不做批量抓取、站点爬取、订阅或离线归档。
- 不做账号、云同步、跨设备。
- 不发布到扩展商店。
- 插件内不做翻译、不碰任何密钥。

## 附录 A：可行性调研结论（2026-09-22 探针实测）

用 Playwright（`channel: "chromium"`）加载一个临时 MV3 扩展，实测两批能力。探针产物未入库（只在 `/tmp`）。

### A.1 写盘机制

| 验证项 | 结果 |
| --- | --- |
| MV3 扩展在 Playwright 中加载运行 | 通过 |
| `chrome.downloads.download()` + data URL 写文件（零服务器） | 通过 |
| 中文文件名 | 通过 |
| 子目录文件名 | 通过 |
| **绝对路径** | **报错 `Invalid filename`** —— 只能写下载目录下的相对路径 |
| 2 MiB 的 data URL | 通过，字节数完整 |
| HTTP(S) 远程 URL 下载 | 通过 |
| 批量 7 个下载同时发起 | 全部 complete |
| Chrome 危险文件判定 | 全部 `danger: "safe"`，不触发警告 |
| 中文内容 UTF-8 | 逐字节正确 |

### A.2 提取与转换管线

| 验证项 | 结果 |
| --- | --- |
| Readability + Turndown + GFM + DOMPurify 打包 | **76 KB**（minified） |
| domino / jsdom 残留 | **0** —— 不依赖 Node 的 DOM |
| Readability 挑正文 | 导航、侧栏、页脚均被剔除 |
| 列表 / GFM 表格 / 围栏代码块 / 加粗 / 链接 / 中文 | 通过 |
| 正文内相对路径图片 | 自动绝对化（Readability 自身行为，无需额外代码） |
| DOMPurify 净化 | `<img onerror>` 剥掉 `onerror`；`<script>` 整体消失；`javascript:` 链接被剥 |

### A.3 由此确认的简化

1. **图片不需要 `fetch`，也不需要 `host_permissions` 绕 CORS**：`chrome.downloads.download()` 对 HTTP(S) URL 会带上该 host 的 cookie，浏览器下载管道直接搞定登录态图片。
2. **不需要常驻服务、不需要 offscreen document**：Markdown 用 data URL 写盘即可。
3. **DOMPurify 用法**：浏览器里 `import DOMPurify from "dompurify"` 得到的已是初始化好的实例，直接 `DOMPurify.sanitize()`，不需要 `createDOMPurify(window)`。
4. **`turndown-plugin-gfm` 是具名导出**：用 `import { gfm } from "turndown-plugin-gfm"`。
