## 1. 这是一条线路：两个产品，靠文件交接

用户的问题发生在浏览器里：读到好文章时想留下 Markdown，但文章可能是登录后才看得到的、图片可能挂在带会话的 CDN 上。这件事**只有浏览器插件能做**，因为只有它手里有当前这份会话。

但插件只管「抓下来」，不管「加工」：图片还在网上，内容可能不是中文。批量加工（图片落到本地、翻译）属于桌面端已有的能力范围。

| | 插件（B） | 桌面端（A） |
| --- | --- | --- |
| 职责 | 用当前会话抓当前页 → 转 Markdown → 连图一起落盘 | 吃一批本地 `.md` → 内嵌图片 / 翻译 → 输出到目标目录 |
| 位置 | 浏览器里 | 本机应用 |
| 输入 | 当前页面 | 一个目录 |
| 输出 | 一个目录 | 另一个目录 |

**连接方式是文件交付，不是主从调用**：插件不需要桌面端在运行，也不需要任何常驻服务。若要插件必须等桌面端在场才能用，「一键导出」就失去意义了。

```
网页 → 插件：提取正文 → 转 Markdown → 写盘（标题.md + 标题.images/）
                                              ↓（可选，另案）
                        桌面端：选目录 → 勾选 → 内嵌图片 / 翻译 → 输出到目标目录
```

图中下半段是**另案**，不是 B 的前置：B 交付的是一对能直接用的文件，谁去加工都行（见 §2）。

## 2. 分工与顺序

| 块 | feature | 内容 | 顺序 |
| --- | --- | --- | --- |
| B | `feat-040` | 浏览器插件：提取正文 → 转 md → 收图 → 落盘 | **先做** |
| A | `feat-042` | 桌面端「文档处理」：选目录 → 列 md → 勾选 → 内嵌图片 / 翻译 → 输出 → 去重 | 另案（无顺序依赖） |

**为什么 B 先（2026-09-24 用户裁定）**：

1. 这条线里**只有 B 需要那份「当前会话」**——登录后才可见的正文、带会话签名的图片。用户一开始想解决的就是这件事。
2. A 可以吃**任意现成的 `.md`**，不依赖 B 存在；反过来 B 也不需要 A 在场（产物是给任何 Markdown 工具用的文件）。两边谁先做都能独立验收，所以按价值排序，B 先。
3. 项目硬约束「同一时间只允许一个 `in-progress`」（`init.sh` 断言）仍然成立，只是次序反过来：现在轮到 B。

**「拆开」的确切含义（2026-09-24）**：

1. **顺序依赖删除**：`feature_list.json` 里 `feat-040 → feat-042` 的依赖已删；A 不再是 B 的前置。
2. **代码不共享**：B 自带转换核心，**不改桌面端任何文件**（理由与代价见 §5.2 与 `docs/features/browser-extension/FSD.md` §3.8）。
3. **契约只剩产物形态**：A 将来按 B 的产物读入，而不是 B 为了迁就 A 改变自己写什么（见 §3）。

## 3. 交接契约（只在本文件写跨产品的那几条）

插件与桌面端之间的**唯一接口是文件系统**。产物长什么样由**生产者**定义：`docs/PRD-browser-extension.md` §4（B 的对外契约，含 `<标题>.md` + `<标题>.images/`、相对引用、抓不到的图留 URL + 标记、覆盖同名、标题净化规则）。本文件只记录**跨产品**的三条，两边都不许各自改动：

| 项 | 约定 | 依据 |
| --- | --- | --- |
| 插件落盘位置 | 系统**下载目录根**（相对路径） | MV3 硬限制：写绝对路径报 `Invalid filename`（探针实测） |
| 图片引用形态 | 正文用**相对路径**引用 `<标题>.images/xxx` | 目录可整体搬移，md 不绑死绝对路径；也是 A 读入时的依据 |
| 去重依据（A 侧实现） | 文件路径 + 内容哈希 + mtime（+ 输出路径） | 只用路径会在改名 / 移动后失效；只用 mtime 判断不了内容是否变化 |
| 桌面端输入 | 用户自选任意目录（默认可指向下载目录） | A 是通用能力，不绑死插件 |

原「待定」两条已于 2026-09-24 裁定：标题非法字符按 `src/lib/markdown.ts:46` 的净化规则处理（无时间戳），同名一律**覆盖**（`uniquify` 会把 `标题 (1).md` 与 `标题.images/` 拆散）——结论见 `docs/PRD-browser-extension.md` §3、§4。

## 4. 共同口径与边界

1. **只读当前页面 DOM**：不读 Cookie、不读登录凭据、不绕过访问限制、不做自动翻页或爬取。
2. **内容不离开本机**：插件不主动联网（除浏览器自己为图片发起的下载）；翻译全部在桌面端，使用用户自己配置的端点。
3. **不静默丢东西**：抓不到的图片留 URL + 标记；处理失败要说原因。
4. **正文提取与文本转换规则一致**（原文写「两端输出必须一致」，2026-09-24 更正）：图片表示两端本来就不同（插件写 `<标题>.images/` + 相对路径，桌面端 base64 内嵌），md 头部时间戳也可能不同，所以「结果逐字节相同」严格讲不成立。真正要一致的是**提取正文与文本转换的规则**（列表/表格/围栏代码/链接内联化/净化不漂移）。本轮不共享代码（§5.2），这条由 B 的核心用同款配置 + 自测自证；等 A 规划时再定要不要统一。

## 5. 线路级工程决策

1. **同仓库（保留，理由修订）**：插件与桌面端在同一个仓库。**2026-09-24 修订**：理由不再是共享代码，而是共用既有依赖、lint/测试工具与文档体系，并让「产物形态」与「桌面端将来的输入形态」由同一份文档约束。仓库边界与代码共享是两件事。
2. **共享代码边界（2026-09-24 改为「延后」）**：原决定是抽出**无 Node 依赖**的一段（Readability + Turndown + GFM + DOMPurify）两端共用，桌面端 `extract.ts` / `markdown.ts` 改成薄壳。**本轮改为 B 自带核心**（`extension/src/convert/`：纯函数 + 注入环境依赖 + 自带单测）：B 先做，而共享必然要改已发布的桌面端两个文件，那是 B 不该承担的范围与风险。将来要统一只是**搬家**（`docs/features/browser-extension/FSD.md` §3.8）。
3. **独立版本线**：插件的版本由扩展自身 manifest 的 `version` 管理，**不进** `desktop:release` 门禁。作废文档里的 `v0.5.0 / v0.6.0 / v0.7.0` 不采纳。
4. **触发方式**：用户主动，独立功能入口 —— 插件侧是浏览器工具栏；桌面端侧是独立页面 / 区块，不是常驻主流功能。
5. **翻译只在桌面端**：插件不碰任何密钥，因此不存在密钥存储问题。

用 Playwright（`channel: "chromium"`）加载一个临时 MV3 扩展，实测两批能力。探针产物未入库（只在 `/tmp`）。

### A.1 写盘机制

| 验证项 | 结果 |
| --- | --- |
| MV3 扩展在 Playwright 中加载运行 | 通过 |
| `chrome.downloads.download()` + data URL 写文件（零服务器） | 通过 |
| 中文文件名 | 通过 |
| 子目录文件名 | 通过 |
| **绝对路径** | **报错 `Invalid filename`** —— 只能写下载目录下的相对路径 |
| 2 MiB 的 data URL | 通过，字节数完整 |

| 中文内容 UTF-8 | 逐字节正确 |

### A.2 提取与转换管线

| 验证项 | 结果 |
| --- | --- |
| Readability + Turndown + GFM + DOMPurify 打包 | **76 KB**（minified） |
| domino / jsdom 残留 | **0** —— 不依赖 Node 的 DOM |
| Readability 挑正文 | 导航、侧栏、页脚均被剔除 |
| 列表 / GFM 表格 / 围栏代码块 / 加粗 / 链接 / 中文 | 通过 |

| DOMPurify 净化 | `<img onerror>` 剥掉 `onerror`；`<script>` 整体消失；`javascript:` 链接被剥 |

### A.3 由此确认的简化

1. **图片不需要 `fetch`，也不需要 `host_permissions` 绕 CORS**：`chrome.downloads.download()` 对 HTTP(S) URL 会带上该 host 的 cookie，浏览器下载管道直接搞定登录态图片。
2. **不需要常驻服务、不需要 offscreen document**：Markdown 用 data URL 写盘即可。
3. **DOMPurify 用法**：浏览器里 `import DOMPurify from "dompurify"` 得到的已是初始化好的实例，直接 `DOMPurify.sanitize()`，不需要 `createDOMPurify(window)`。
4. **`turndown-plugin-gfm` 是具名导出**：用 `import { gfm } from "turndown-plugin-gfm"`。
